# Historical reviewed proposals

The owner-only factory dashboard reads at most 20 completed terminal reviews and three completed predecessors plus at most two ledger-verified failed-build recoveries per review. Only a complete discover/build/simulate/review chain with matching owner, project, root, order revision, base/head, PR identity and the existing proposal evidence gate is displayed. Evidence is validated at recorded completion time, so reopening historical work does not manufacture a new execution.

The order link is always historical and its current validity is unverified: edited or deleted orders must never appear fulfilled. Stored artifact references are factory evidence metadata, not independent re-fetching of artifact contents. No provider calls, admission, expenses, publishing, order completion, career-generation attribution or life scoring occurs. Failed-build recovery is accepted only through the existing owner-scoped recovery ledger verifier and matching rebase/attempt identity. Ordinary repair loops outside this conservative stage shape remain absent until separately supported and verified. This feature does not make the code/GitHub career operational.

Validation: focused fixtures cover owner isolation, chain breaks, order/version identity, unsafe PR URLs, incomplete or self-reviewed evidence, duplicate polling and historical timestamps. Run tests/software-factory-order-evidence.test.ts and existing factory route tests. Deployment and full App QA are separate gates.

## Office review loop (factory draft PR -> office reviewer -> academy)

Off by default. With `SOFTWARE_FACTORY_OFFICE_REVIEW_ENABLED=true` in the factory worker environment, each order-scheduling pass first runs a reconciliation sweep (`server/software-factory-office-review.ts`) over the same verified proposals shown above. Every proposal with a recorded draft PR gets exactly one `claude_review` job in `agent_office_cloud_jobs`, marked `source: "factory"`, whose idempotency key is a permanent UUID digest of (owner, factory review job id, exact head SHA). Retries, restarts and concurrent sweeps return the existing row; a new head is a new key. The insert runs under the existing owner advisory lock and is capped per UTC day at the operator's `maxDraftPullRequestsPerDay`. The factory makes no provider call for this, and a failed handoff is logged and reconciled on the next pass without blocking order scheduling.

The review-only office worker (same owner, `OFFICE_WORKER_REVIEW_ONLY=true`) claims it on its existing path: role reservation, credit-limited run (`OPENAI_SHARED_CREDITS_REQUIRED` ledger), exact head plus full diff SHA-256 binding, verdict and findings, fenced completion, `completeRoleExecution` and `advanceCompany` scoring in `finish()`. The reviewer has no write access; nothing merges, dispatches, publishes or closes an order.

The factory dashboard links the stored verdict back to each proposal as `officeReview` (`pending`, `running`, `pass`, `block` with findings count, `failed`, `head_mismatch`, `unavailable`). It is read-only. A verdict counts only when the stored review is bound to the same PR URL and the head recorded by the factory. Finding text is not copied into the factory view.

Academy: real factory reviews are scored exactly like other real reviewer executions. Qualification and promotion stay benchmark-gated (`OFFICE_REVIEW_BENCHMARK_PROMOTION_ENABLED`, held-out fixtures). Remaining work: the `production` assessment scope in `shared/office-role-lifecycle.ts` (`recordProductionPolicyAssessment`) has no producer yet. A trusted evaluator that compares a candidate policy with the incumbent on the same real PR would be needed before real work could count toward promotion. It is intentionally not stubbed.

Validation: `tests/software-factory-office-review.test.ts` (it is not yet in the pinned `factory-candidate-checks.yml` list; adding it changes the workflow SHA-256 the operator configuration pins).
