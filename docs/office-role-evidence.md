# Owner-scoped role evidence and evaluation

This release adds source audits and bounded comparative evaluation for the fourteen previously unsupported role IDs. It does not make their external business functions operational, deduct life for unavailable infrastructure, or automatically replace holders. No generated score can activate a role.

The PC reads five owner-bound SQL sources (control permissions, automation definitions, investment cost basis, revenue ledger and project document inventory). Seven web-owned sources are exported by the existing web host to PostgreSQL: News and its two city lanes, BlackRoom queue, Dropshipping, Marketing and Clippers. Code and GitHub are audited from a read-only GitHub source (below). Source timestamps and missing/invalid/empty states remain distinct. No publication, trade, charge, customer message or provider call is performed by source export/audit.

Create `office_web_role_sources` using the reviewed `OFFICE_WEB_ROLE_SOURCE_SCHEMA_SQL` export in `server/office-web-role-store.ts` before enabling exports. Startup never runs migrations. Web configuration requires `AGENT_COUNCIL_STORAGE=postgres` and `OFFICE_WEB_SOURCE_EXPORT_ENABLED=true`; the canonical system owner must exist. The exporter reads once per minute without a browser. The PC wakes the existing host through its public health endpoint before consuming exports; older than five-minute observations are refused. Old underlying data never gains a new source timestamp.

PC flags default disabled: `OFFICE_ROLE_WORK_ENABLED`, `OFFICE_WEB_SOURCES_ENABLED`, `OFFICE_ROLE_ACADEMY_ENABLED`. Web-source consumption also requires an HTTPS origin in `OFFICE_WEB_SOURCE_ORIGIN`. Academy requires explicit `OFFICE_ROLE_ACADEMY_DAILY_PAIRS` (1–14), `OPENAI_SHARED_CREDITS_REQUIRED=true` and an absolute `OPENAI_SHARED_CREDIT_CONFIG` path beside the protected worker configuration. The existing shared ledger must already contain the independently verified grant. No startup initializes or replenishes credits. Existing monthly token allowance remains in force; evaluation output is capped at 1536 tokens per call.

Worker-side database observation: the web host is autoscaled and private, so it is often asleep and cannot be woken from the cloud worker. For roles with a canonical database source (`blackroom-videos`: `blackroom_remote_control`; `marketing-cmo`: marketing learning in `revenue_engine_state`), the worker prefers a host export younger than four minutes and otherwise observes the database itself with the same projection, provenance digests and validation (`server/office-web-role-live.ts`). That observation never reads files (parts without a durable database copy are reported `missing`; see the durable web-source documents section below) and is never persisted, so it cannot overwrite a richer host export. The host exporter uses a single connection with a 20 s connect timeout and a bounded retry of connection-level failures only.

The current curriculum is **narrow synthetic evidence triage**, not full role training: three distinct paired cases per role/generation, at most one pair per role per 24 hours, one academy assignment at a time across the reviewer and role curricula. Baseline and candidate results have provider response IDs, measured tokens, timing, source citations and independently computed grades. Unknown calls retain fences and are not retried. Candidate cost comparison remains pending priced receipts; `candidateQualified` and `promoted` stay false. Continuous incumbent training, production capability matching and verified first execution are required before replacement can be claimed.

Deploy the compatible web parser before enabling the PC flags; reconcile the exact protocol rollout revision. Stop the existing Windows worker cooperatively and wait for its ownership lock to drain before replacing its checkout/configuration. Do not create another scheduled worker. Preserve council, token, shared-credit and audit history. On rollback, stop new admissions first, drain outstanding work, disable flags and reconcile uncertain reservations. Older code may not validate new journals: do not roll back the authoritative parser across persisted curriculum/source versions without a reviewed migration.

Verification includes canonical owner isolation, JSONB reordering, stale and malformed sources, generation changes, restarts, competing workers, budget refusal, uncertain calls, and a real compare-and-swap conflict preventing a reviewer call after losing its reservation. Automated fixtures are not live execution evidence; production checks must be reported separately.

## Durable web-source documents (office_source_documents)

Production runs on Replit Autoscale, whose disk is ephemeral: the files under `dropshipping_engine_data/`, `clippers_workspace/local-news/state.json`, `clippers_workspace/metrics/metrics-summary.json` and `clippers_workspace/reports/*.json` are gitignored, lost on every restart and invisible to the cloud worker. The producers now also write a validated projection of each of these documents to one owner-scoped table, `office_source_documents` (`server/office-source-documents.ts`), keyed by `(owner_key, kind, doc_key)`: `doc_key` is empty for singleton documents and the report filename for Clippers daily/cycle reports. One generic table is used because every kind shares the same lifecycle (whole-document replace by its single producer), bounds and reader.

- Only the fields the audit needs are stored (ids, timestamps, enum states, numeric counters). Copy, URLs, media, captions, customer/supplier details, posts, summaries, tokens and paths are dropped; projections are strict zod objects. A document that fails validation or exceeds 1 MB is stored as an explicit `invalid`/`limit` marker with no content, so an older valid copy can never mask it.
- Writes are a guarded upsert: a write older than (or identical to) the stored one is a no-op, `revision` increments otherwise. Reports keep the newest 60 per owner. CHECK constraints bind kinds, key formats, status/content consistency and size.
- Write-through is enabled only with `OFFICE_SOURCE_DOCUMENTS_ENABLED=true` and `AGENT_COUNCIL_STORAGE=postgres`, and only for the exact canonical file paths the reader uses. The file write is kept. Persistence is asynchronous, serial and coalesced; failures never break the producer and never log details.
- `readWebRoleSources` prefers the durable document per kind (same projections, provenance with `files: 0`, digests and validation) and reads files only for kinds without a copy, and only on the web host. A failed database read is invalid evidence, never a file fallback. Before the migration the table is absent and readers behave as before.
- All seven web roles are now in `DATABASE_WEB_SOURCE_ROLES`: when no fresh host export exists the cloud worker observes them from the database. Kinds still without a durable copy stay `missing` and the audit stays blocked.
- Clippers reports: a fixed allowlist of known non-report artifacts in `clippers_workspace/reports/` (for example `metricool-approval-report.json`, `clippers-external-closeout-pack.json`) is skipped by exact name; any other unexpected file still marks the folder invalid.

Migration (owner action, never run at startup or request time): `node --import tsx script/office-source-documents-migrate.ts` creates `office_source_documents` and `office_web_role_sources` inside a transaction, verifies them and rolls back; `--apply` commits. It is additive (`CREATE TABLE IF NOT EXISTS` only). Suggested addition to the manual factory operations workflow (not edited here): actions `office-sources-migrate-dry-run` and `office-sources-migrate-apply` (the latter gated by `confirm=APLICAR`), running that script with `DATABASE_URL` from the office database secret. Then set `OFFICE_SOURCE_DOCUMENTS_ENABLED=true` on the web host and redeploy it; durable copies appear as each producer next writes its file (local news every few minutes; dropshipping and Clippers on their next mutation/run). Rollback: unset the flag (producers keep writing files; readers then use any remaining copies, so `DELETE FROM office_source_documents` or `DROP TABLE office_source_documents` returns fully to file-only behaviour).

## Incumbent training on real audit triage

`OFFICE_CAPABILITY_TRAINING_ENABLED=true` enables the distinct `source-triage-v1` capability. It requires role audits, the same shared credit ledger and explicit `OFFICE_CAPABILITY_MAX_CALLS_PER_DAY` (1–28; rollout allocation 14, within the existing monthly token limit). The existing worker checks once per minute, with one academy assignment at a time and a 768-token response ceiling. Keep the unrelated synthetic role-pair series disabled during this rollout.

The current holder classifies a real, hashed source audit. Deterministic grading checks exact evidence IDs, issue codes and source-first decisions. Confirmed errors yield bounded lessons with the originating run retained. Three paired held-out comparisons on three dates must show improvement in at least two, no regression and no higher measured ledger cost or elapsed time. A qualifying policy enters probation on the same holder/generation; only its next verified real triage activates it. Failure restores the previous policy. No error or tie is manufactured to force a promotion. These policies do not add publishing, legal, financial or development competence and never replace the business-role holder.

The cost reader requires an already-settled Office receipt matching execution, response, model and priced token usage. Missing or uncertain receipts stop training without replay. The journal stops admission at 200 runs or 100 policies; retention/reconciliation must preserve historical proof. Do not change grader, lesson or held-out semantics under the same capability version; use a versioned evaluator/migration. The feature does not initialize balances, increase spending allocations or add permissions.

## GitHub source for `github` and `code`

`server/office-github-role-source.ts` reads the owner's registered repositories from `app_projects` (`github_repo`, or `repo_owner`/`repo_name`; only github.com, lower-cased, de-duplicated, sorted, at most 10) in a read-only, owner-bound transaction, then calls the GitHub REST API with GET only: origin fixed to `https://api.github.com`, `redirect:"error"`, 10 s per request, a 40 s overall deadline inside the 60 s role-work lease, concurrency 4 and the first blocking error cancelling sibling requests. It never writes to GitHub and never calls a model.

- `github`: repository metadata (default branch, `pushed_at`, `open_issues_count`, archived) and the latest Actions run on the default branch. Findings: `FAILING_DEFAULT_BRANCH`, `STALE_REPOSITORY` (no push in 30 days), `REPOSITORY_ARCHIVED`, `WORKFLOW_UNREADABLE`, `REPOSITORY_UNREADABLE`, `PARTIAL_COVERAGE` (more than 10 registered).
- `code`: open pull requests (at most 30 in total, 30 per page, at most 3 pages per repository): draft, age, requested reviewers/teams, check-runs summary for the head commit and, only with a token, `mergeable_state`. Findings: `PR_FAILING_CHECKS`, `PR_STALE` (no update in 7 days), `PR_NEEDS_REVIEW` (non-draft, older than 24 h, pending requested review or `mergeable_state=blocked`), `PR_CONFLICTED`, `CHECKS_UNREADABLE`, `REPOSITORY_UNREADABLE`, `PARTIAL_COVERAGE`. No open PRs is a completed audit without findings.

Record ids are stable digests of `owner/repo` (and PR number) and are verified on every parse. Snapshots carry `github:{blocked,truncated,repositories}`; SQL snapshots are unchanged. A read that succeeds is `completed` even with findings. Expected failures are persisted as a `blocked` snapshot with one precise code: `NO_REGISTERED_REPOSITORIES`, `GITHUB_TOKEN_INVALID`, `GITHUB_AUTH_REJECTED` (401), `GITHUB_RATE_LIMITED` (429, or 403/401 with `x-ratelimit-remaining: 0`/`retry-after`), `GITHUB_TIMEOUT`, `GITHUB_READ_DEADLINE`, `GITHUB_NETWORK_ERROR`, `GITHUB_UPSTREAM_ERROR`, `GITHUB_RESPONSE_INVALID`; if no repository is readable the audit is `blocked` with `REPOSITORIES_UNREADABLE`. Inventory/database failures throw and are recorded as `SOURCE_UNAVAILABLE` (`reason: source_unavailable`). Raw error messages, URLs and the token are never stored or logged; the token appears only in the `Authorization` header.

The reader runs whenever `OFFICE_ROLE_WORK_ENABLED=true` (no new flag). Workers without the reader, and historical journals, keep the earlier `CAPABILITY_UNAVAILABLE` audit, which still validates. Completed and blocked GitHub audits feed `source-triage-v1` like any other role audit; capability training semantics are unchanged.

Owner action: set the repository secret `OFFICE_GITHUB_TOKEN` (exposed to the cloud worker as `GITHUB_TOKEN`) to a fine-grained, read-only token limited to the registered repositories with Metadata, Contents, Pull requests and Actions read (plus Checks/Commit statuses read where offered). Without it only public repositories are read (60 requests/hour, so `mergeable_state` is skipped) and private repositories report `REPOSITORY_UNREADABLE`.

## Self-heal: detect → fix → verify (`OFFICE_SELF_HEAL_ENABLED`, default off)

`server/office-self-heal.ts` turns a strict allowlist of small code findings into system-authored company orders and verifies the fix with independent checkers. Off unless `OFFICE_SELF_HEAL_ENABLED=true` (requires `OFFICE_ROLE_WORK_ENABLED=true`).

- Allowlist: `github:FAILING_DEFAULT_BRANCH` and `code:PR_FAILING_CHECKS` (draft PRs only), both only on `robertmanzanillag-jpg/blackops`. A self-heal fix PR is never itself a target (no loops). `automations:RECORDED_FAILURE` is not included: the automation snapshot has no link to repository code, so attribution would be a guess. Every other finding is counted as detected only.
- Data-absence findings (`SOURCE_MISSING`, `NO_RECORDS`, `NO_SOURCE_RECORDS`, `SOURCE_UNAVAILABLE`, `EXPORT_*`, `CAPABILITY_UNAVAILABLE`, GitHub access block codes) never become orders; they are kept as "needs owner/data" notes until the data returns.
- Orders: at most `OFFICE_SELF_HEAL_MAX_ORDERS_PER_DAY` (1 by default, hard maximum 2, below the factory cap of 5) per UTC day, counted from the durable ledger, retries included. Idempotent per (role, code, record id); a verified problem that regresses opens a new episode. The text is a fixed template built only from codes, the record id prefix and a validated PR number (≤ 500 chars, no KONG text), with one engineering assignee (`github` or `code`). The marker `order.selfHeal` is never set by routes. KONG roles and repositories are excluded.
- Admission: the factory admits these orders only when the operator config sets `autoAdmit.systemOrders: true` (default false) and the order text equals the re-derived template. Owner orders are unchanged. All factory guardrails (draft PRs, write scope, daily cap, `autoAdmit.maxPerDay`, credit ledger) still apply.
- Checkers before anything is done: (a) factory checks + independent review (a verified proposal exists only when `proposalEvidenceGate` passed); (b) the office review verdict on the exact head (`block` fails the attempt); (c1) the next complete `code` audit shows the fix PR without `PR_FAILING_CHECKS`/`PR_CONFLICTED`/`CHECKS_UNREADABLE`, and the finding's role shows no new finding of higher severity; (c2) after the fix PR leaves the open list, the next daily audit of that role no longer contains the original finding and no new higher-severity finding. A failed checker reopens once (attempt 2/2); a second failure escalates to the owner. Factory infrastructure stops (credit, caps, pause, unknown) and an order not admitted within 72 h go to the owner without consuming the retry. A finding that disappears before any proposal is recorded as cleared.
- Evidence: the chain finding → order → factory root job → PR (url, base/head) → independent review → office review → pre-/post-merge re-audit is stored in `officeExecution.selfHeal` and mirrored on `order.selfHeal.chain`. The factory worker records its part (`server/office-self-heal-factory.ts`, same flag) from committed rows only.
- Merge policy: nothing merges, deploys or dispatches automatically. `readyToMerge` is a display flag, true only when every pre-merge checker passed. Merging stays a human decision (AGENTS.md); the post-merge audit then marks it "reparado y verificado".
- Office: per agent "problemas detectados / en reparación / reparados y verificados / necesitan al dueño" (counts only, `selfHeal` in `/api/agent-council/state`).
- Rollback: unset `OFFICE_SELF_HEAL_ENABLED` on both workers and `autoAdmit.systemOrders`; the ledger stays as history and open system orders are no longer admitted.

Validation: `tests/office-self-heal.test.ts` and the systemOrders case in `tests/software-factory-asistente-operator.test.ts` (the new file is not in the pinned `factory-candidate-checks.yml` list; adding it changes the workflow SHA-256 the operator configuration pins).
